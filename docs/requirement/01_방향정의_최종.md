## 1. 서비스 정의

> 지출을 기록하는 가계부처럼, **자산의 변화를 기록**하고
> 분석 · 비교해 **자산을 늘리도록 돕는 자산 가계부**

### 가계부 vs 자산 가계부

| 구분 | 가계부 | **자산 가계부** |
|---|---|---|
| 기록 대상 | 지출 내역 | **자산의 변화** (일별 자산, 종목 변동) |
| 기록 방식 | 사용자가 직접 입력 | **자동 수집** (CODEF · 시세 API) |
| 보여주는 것 | 어디에 얼마 썼나 | **얼마나 변했나, 왜 변했나** |
| 결산 | 월별 지출 합계 | **월간 자산 결산** (변화액 · 주요 이벤트 · 목표 진척) |
| 행동 | 지출 줄이기 | 목표 점검, 예적금 갈아타기 |

> 가계부의 익숙한 사용 경험(기록 → 추이 → 결산)은 그대로 가져가고,
> **기록의 대상만 지출에서 자산으로 바꾼다.**

### 서비스 구조

```
┌──────────────────────────────────────────────────┐
│  전달      알림 (웹 푸시 중심)  ·  대시보드          │
├──────────────────────────────────────────────────┤
│  핵심 기능  자산을 늘리기 위한 서비스                 │
│   ① 종목 급등락 원인 분석                           │
│   ② 투자 목표 관리                                  │
│   ③ 예적금 비교 · 만기 갈아타기                      │
├──────────────────────────────────────────────────┤
│  기반      자산 가계부 — 자산을 보여주고 팔로잉한다    │
│   · 자산 변화 자동 기록  · 추이 (전일/전월/전년)      │
│   · 월간 자산 결산                                  │
└──────────────────────────────────────────────────┘
```

**기반이 서비스의 본체**이고, 핵심 기능 3개는 그 위에서 자산을 늘리기 위한 도구다.
기반이 없으면 핵심 기능이 설 자리가 없고, 핵심 기능이 없으면 숫자만 보여주는 앱이 된다.

### 한 줄 컨셉
**숫자만 보여주는 자산 앱은 많다. 자산 가계부는 그 숫자가 어떻게, 왜 변했는지 기록하고 말해준다.**

### 리텐션 원칙
> **알림은 문을 여는 열쇠, 페이지는 머무는 이유.**
> 알림이 재방문을 만들고, 자산 기록 · 원인 분석 · 목표 진척이 체류를 만든다.

## 3. 기반 — 자산 가계부

> 자산을 **보여주고 팔로잉**하는 층. 정해진 일일 수집 시점에 자동으로 기록되고, 쌓인 기록이 추이와 결산이 된다.

### 3.1 자산 변화 자동 기록
- 정해진 일일 수집 시점에 연동 자산(증권 · 예적금 · 현금)을 스냅샷으로 자동 기록한다. 주식 시세가 필요한 계산은 거래일 기준으로 처리한다
- 실행 시각은 **영업일 16:00**(장 마감 15:30 + 여유). 휴장일(주말 · 공휴일)은 한투 기준 종목의 최신 거래일로 판정해 수집 · 기록을 건너뛴다. **판정할 수 없으면(외부 API 장애 등) 휴장으로 처리하지 않고 그 실행을 중단**한다. 장 마감이 늦어지는 날(수능일)은 마감 뒤 따로 실행한다 (§14 #23 · #25)
- 종목별 평가금액 · 손익 · 당일 변동을 함께 기록
- 연동 가능한 자산은 자동으로 기록되며, **사용자가 매일 직접 입력할 필요가 없다** — 가계부의 가장 큰 이탈 원인(수기 입력)을 제거

#### 기록 범위
| 자산 | 기록 | 자산군 | 비고 |
|---|---|---|---|
| 국내 주식 | 포함 | 증권 | |
| 국내 ETF | 포함 | 증권 | 원인 분석은 지수 · 시장 움직임 중심 (§4 ①) |
| 증권 계좌 예수금 | 포함 | 현금 | 현금성 자산 |
| 은행 입출금 계좌 | 포함 | 현금 | 수기 입력 — 현금(CASH) 유형으로 등록하고 이름으로 구분 (CODEF 은행 수집은 이후 개발) |
| 예금 · 적금 | 포함 | 예적금 | 상품 비교 범위는 §4 ③. 수기 입력 (CODEF 은행 수집은 이후 개발) |
| 수기 자산 | 포함 (등록 기능 필수 · 등록 여부는 사용자 선택) | 예적금 / 현금 | 예금 · 적금 · 입출금 · 현금을 이번 범위에 넣는 유일한 입력 경로. 한 번 등록(매일 입력 아님). 유형은 예금 · 적금 · 현금, 예금 · 적금은 상세(금리 · 만기 등) 필수. 삭제해도 과거 기록 보존(비활성 처리). 가치 갱신 방식 `[구현 시 확정]` |
| 해외 주식 | **제외** | — | 향후 확장 |

#### 변화의 구분 — 총자산 변화 ≠ 운용 성과
자산 가계부는 투자 성과만이 아니라 **사용자의 전체 자산 변화**를 기록한다.
월급 · 추가 저축으로 벌어 남긴 돈이 자산으로 들어오는 것도 **정상적인 자산 증가**다. 다만 시장가격에 의한 변화는 구분해서 보여준다.

| 구분 | 정의 |
|---|---|
| 총자산 변화 | 월급 · 추가 저축 · 이자 · 주가 상승 등 모든 자산 변화 |
| 시장가격 영향 | 주식 등 보유 자산의 가격 변동으로 생긴 평가액 변화 |
| 기타 자산 변화 | `총자산 변화 − 시장가격 영향` — **원인을 뜻하지 않는 차이값** |

> 예) 전월 3,000만 원 → 추가 유입 100만 원 · 주식 평가액 +30만 원 → 현재 3,130만 원
> 화면: **이번 달 총자산 +130만 원 / 시장가격 영향 +30만 원 / 기타 자산 변화 +100만 원**

- 기타 자산 변화의 원인은 추측하지 않는다 — "월급이 들어와서 100만 원 증가했습니다" 같은 문장은 생성하지 않는다
- 필요 시 설명: "입출금, 예적금 변동, 매매 등 시장가격 이외 요인이 포함될 수 있습니다"
- 매수 · 매도는 현금 ↔ 증권 사이의 **내부 이동**(총자산 변화 0)이므로 그 자체를 자산 증가 원인으로 표현하지 않는다
- 시장가격 영향 = 직전 COMPLETE 기록 대비 **계속 보유한 수량**의 가격 변화 합. 매수 · 매도로 늘거나 줄어든 수량은 가격 효과를 계산하지 않고 기타 자산 변화에 들어간다(체결 단가 · 시각 미수집). 공식 · NULL 조건은 05 §4.7 (§14 확정 2026-10-28)
- 예금 이자 별도 식별, CODEF의 자산 이동 데이터 제공 여부, 외부 입출금 데이터 활용 `[확인 필요]` (§14 #3)

#### 기록의 완전성
| 상태 | 의미 |
|---|---|
| COMPLETE | 해당 날짜에 필요한 자산 데이터를 정상 수집하고 계산 완료 |
| PARTIAL | 일부 금융기관 · 계좌 · 종목 데이터 누락 |
| FAILED | 정상 스냅샷을 만들기 어려울 정도로 수집 실패 |

- 스냅샷마다 **수집 상태**와 **실제 수집 시각**을 기록한다
- PARTIAL · FAILED 기록은 수집 이력 · 오류 확인용으로 남기되 다음 계산에서 **제외**한다: 전일 · 전월 · 전년 대비, 총자산 변동 감지, 상승 하이라이트, 목표 진척, 월간 결산, 자산 증가 추이
- 원칙: **잘못된 값으로 계산하는 것보다 그 날짜의 비교값이 없는 것이 낫다**
- 실패한 자산을 직전 값으로 이월해 정상 데이터처럼 만들지 않는다 (예: 9/28 예금 해지 + 조회 실패 시, 9/27 값을 복사하면 없는 예금이 있는 것처럼 기록된다)
- 비교 기준은 **직전 COMPLETE 기록**이다 — 월 COMPLETE → 화 PARTIAL → 수 COMPLETE이면 수요일은 월요일과 비교
- 주식 평가금액은 **동일 기준 시점의 보유수량과 시세**로 계산한다 — 그 배치 실행에서 받은 보유수량 × 한투 원주가 종가(종목별 소수 2자리 반올림). 거래정지 종목은 직전 거래일 종가로 평가한다. 예수금 필드의 의미 · 체결 직후 수량 반영 시점 `[확인 필요]` (§14 #4)
- 화면 표시("직전 정상 기록 대비" 문구 여부, "마지막 확인 금액 · 확인일" 표시 등) `[구현 시 확정]`

#### 기록 시작 시점
- 사용자 자산 기록은 **계좌 연동일부터** 시작한다
- 최초 연동 시에는 보유 종목의 최근 30일 가격 · 급등락 이력 · 최근 시장 흐름만 제공한다
- 현재 보유수량 × 과거 가격으로 **과거 총자산 · 자산군 금액 · 목표 진척 · 월간 결산을 만들지 않는다** — 그 사이 매매가 있었다면 사실이 아니기 때문이다

### 3.2 자산 추이
| 비교 기준 | 단위 |
|---|---|
| 전일 대비 | 총자산 · 자산군 · 종목 |
| 전월 대비 | 전월 동일 시점 기준 |
| 전년 대비 | 전년 동월 기준 |

- 모든 비교는 **COMPLETE 기록끼리** 한다 (§3.1)

- 기간 탭: 1개월 / 1년 / 전체
- **상승도 눈에 띄게** — 하락 경고만 하는 앱은 열기 싫어진다. 기타 자산 변화에 의한 증가도 상승으로 보여주되, 시장가격 영향과 기타 자산 변화를 구분해 표시한다
- 차트의 특정 날짜를 누르면 그날의 이벤트(급등락 · 원인)가 표시된다

### 3.3 월간 자산 결산 ★ 신규
> 가계부의 월말 결산 자리. 한 달의 자산 기록을 한 장으로 정리한다.

| 항목 | 내용 |
|---|---|
| 이번 달 변화 | 총자산 증감액 · 증감률, 전월 대비, **시장가격 영향 · 기타 자산 변화** |
| 자산군별 증감 | 증권 · 예적금 · 현금이 각각 얼마나 늘고 줄었는지 ("기여"는 운용 성과로 오해될 수 있어 사용하지 않음) |
| 주요 이벤트 | 이번 달 급등락 이벤트 상위 3건과 원인 요약 (①의 결과 재사용) |
| 가장 많이 오른 · 내린 종목 | 종목별 월간 손익 순위 |
| 목표 진척 | 월초 대비 목표 진척률 변화 (②의 결과 재사용) |
| 다음 달 체크 포인트 | 만기 예정 예적금, 목표 대비 필요 납입액 (③ · ②의 결과 재사용) |
| 한 줄 총평 | LLM 생성 — 월 1회 |

- 월초 · 월말 값은 해당 월의 **첫 · 마지막 COMPLETE 기록**을 사용한다
- 한 줄 총평이 없어도(LLM 실패 · 한도 초과) 수치 결산만으로 완성된다
- 발송: 매월 1일, 웹 푸시(요약) + 텔레그램(전문, 연결한 사용자만)
- 화면: 결산 페이지에서 지난 달들의 결산을 넘겨볼 수 있다 (체류 장치)

> **새 분석을 만들지 않고 핵심 기능 3개의 결과를 모아 보여주는 기능**이다.
> 개발 비용 대비 가계부 경험을 완성하는 효과가 크다.

## 4. 핵심 기능 — 자산을 늘리기 위한 서비스

### ① 종목 급등락 원인 분석 ★ 주력
보유 종목이 크게 움직이면, 그 시점의 공시 · 뉴스 · 거시지표를 수집해 **원인 후보가 될 수 있는 관련 근거**를 제시한다.

```
감지(±5%) → 수집(공시·뉴스·지수) → LLM 요약 → 알림 → 원인 분석 페이지
```

- 상승 · 하락 모두 감지
- 급등락 기준: **전 거래일 대비 당일 가격 변동률**, 기본 ±5% (사용자 조정 가능)
- 시세 API가 제공하는 전일 대비 변동률 사용을 우선 검토한다. 기업행사(액면분할 · 권리락 · 무상증자 · 거래정지 후 재개)에 따른 왜곡이 없도록 기준가 반영 여부를 실제 응답으로 검증한 뒤 확정한다 `[확인 필요]`
- 내 종목만의 움직임인지 시장 전체의 움직임인지 구분 (지수 대비 초과 변동)
- 근거마다 출처 · 시각 · 원문 링크 제공
- **ETF**는 개별 기업과 같은 공시 · 뉴스 분석을 적용하지 않고 지수 · 시장 움직임 중심으로 보여준다. 구성종목 분석 · ETF 전용 뉴스는 범위 미확정 `[구현 시 확정]`

**총자산 급변은 이 기능의 대상이 아니다.** 총자산은 입금 · 만기 · 출금 등 시장 밖 요인으로도 움직이므로 뉴스를 수집하지 않고, 증권 · 예적금 · 현금 변화, 주요 종목 변화, 시장가격 영향, 기타 자산 변화로 설명한다. 감지 임계치는 현재 기본값 3%(조정 가능)이며, 데이터가 쌓인 뒤 너무 자주 감지되는지 보고 조정한다 `[구현 시 확정]`

### ② 투자 목표 관리
목표 금액 · 시점 · 월 납입 가능액을 입력받아 **진척률과 도달 시점 시뮬레이션**을 제공한다.
"이 날짜에 반드시 달성합니다"라는 예측이 아니라, **현재 자산과 월 납입액을 기준으로 계산한 결과**다.

```
목표 입력 → 진척 추적 → 시뮬레이션 → "현재 자산과 월 납입액 기준(수익률 0% 가정), 목표일보다 약 7개월 늦게 도달합니다"
```

| 기본 계산 입력 | 값 |
|---|---|
| 현재 자산 · 목표 금액 · 목표 시점 · 월 납입 가능액 | 사용자 자산 기록 + 사용자 입력 |
| 예상 수익률 | **0%** (기본 시나리오) |

> 예) 현재 3,000만 원 · 목표 5,000만 원 · 월 100만 원 · 수익률 0% → (5,000 − 3,000) ÷ 100 = **약 20개월**

- 최근 3개월 자산 증가액은 **계산 공식에 넣지 않는다** — 과거 증가에 이미 납입이 포함돼 중복 반영되기 때문이다. 필요하면 참고 지표로만 보여준다
- 주가 상승 등으로 현재 자산이 늘면 다음 계산에서 현재 자산이 커지므로 도달 시점이 자연스럽게 당겨진다
- 시나리오 슬라이더: 월 납입액을 바꾸면 도달 시점이 실시간으로 갱신
- 수익률 슬라이더 · 사용자 수익률 입력은 향후 검토 — 의미 · 복잡도 · 수익률 예측으로 오해될 가능성을 보고 결정 `[구현 시 확정]`
- 코멘트는 매일 생성하지 않고 **의미 있는 상태 변화 또는 결산 시점**에만 생성한다 (§7)
- 대시보드에 진척 게이지 상시 노출

### ③ 예적금 비교 · 만기 갈아타기
금감원 공시 기반으로 비교 가능한 상품의 **예상 수령액을 금액으로** 계산해 비교한다.

- **보유 예적금 만기 관리** — 만기 D-30 / D-7 알림
- **정기예금 상품 비교**를 우선 구현한다. 적금은 자산 기록에는 포함하지만, 적금 상품 비교까지 포함할지는 개발 진행 상황을 보고 결정 `[구현 시 확정]`
- **목표 시점 이내 만기 상품 우선 노출** — ②와 ③을 잇는 연결 고리
- 비교 가능한 상품의 금리 · 기간을 기준으로 예상 수령액을 계산해 비교하고, 계산 기준을 함께 표시한다. 기본 / 우대금리, 우대조건 충족 처리, 세후 금액, 기관별 가입제한 반영 범위 `[구현 시 확정]`
- 더 나은 상품이 없으면: **"현재 비교 가능한 상품 중 입력한 조건에서 더 높은 예상 수령액의 상품을 찾지 못했습니다"** — 비교 범위를 넘어서는 "현재가 가장 유리합니다" 같은 단정 표현은 쓰지 않는다

> "증권과 예적금 중 뭐가 유리한가"는 기준이 애매하지만,
> **"목표 시점에 맞는 예치 기간 상품"**은 기준이 명확하다.

### 향후 확장
1. **대출 비교** — 예적금 비교 모듈 재사용, 공시 API의 대출 상품군만 추가
2. 지출 데이터 연동 — 여유자금을 목표 납입액과 연결
3. 해외 주식 · 환율 반영
4. 소셜 로그인 (OAuth 2.0) — 사용자 테이블은 확장 대비로 비밀번호 NULL을 허용해 둠

## 7. AI 활용 상한 정책 ★ 신규

> LLM은 원인 요약 · 목표 코멘트 · 월간 총평에만 사용한다. 나머지 계산은 전부 규칙 기반이다.

### 7.1 호출 지점과 한도
| 호출 지점 | 빈도 | 한도 |
|---|---|---|
| 급등락 원인 요약 | 이벤트 발생 시 | 종목 · 날짜 **분석당 1회**, 사용자당 **신규 분석 생성 요청 일 10건** |
| 목표 코멘트 | 상태 변화 · 결산 시 | **이벤트 기반** — 일일 정기 생성 없음. 후보: 목표 생성 · 금액/시점 변경 · 달성 · 기한 임박 · 월간 결산. 호출 이벤트 목록 `[구현 시 확정]` |
| 월간 결산 총평 | 월 배치 | 사용자당 월 1회 |
| 지출 분류 등 기타 | — | 사용 안 함 |

> **사용자당 일 10건의 의미**: 사용자당 신규 분석 생성 요청은 일 10건으로 제한한다. 이미 생성된 종목 · 날짜 공유 분석을 재사용하는 경우 신규 생성 한도에 포함하지 않는다.
> 한도 수치는 현재 기본값이며, 운영 지표로 실제 사용량을 확인해 조정한다 `[구현 시 확정]`

### 7.2 절감 장치
| 장치 | 내용 |
|---|---|
| **종목 · 날짜 단위 공유 분석** | 동일 종목 · 동일 날짜 분석 결과는 **한 번 생성하여 DB에 저장**하고 여러 사용자가 재사용한다. Redis는 생성 중복 방지와 조회 보조에 사용한다. 사용자별 문구(내 비중 · 내 손익)는 템플릿으로 채운다 |
| 재생성 금지 | 한 번 생성된 요약은 DB에 저장하며 재호출하지 않는다 |
| 근거 없으면 호출 안 함 | 근거 0건이면 LLM 없이 "특별한 뉴스를 찾지 못했습니다" 템플릿 사용 |
| 우선순위 처리 | 일 한도 초과 시 변동률 큰 순으로 요약, 나머지는 근거 목록만 제공 |
| 전역 예산 | 일일 · 월간 전체 호출 예산을 설정, 초과 시 **요약 생략 모드**로 전환 (근거 목록은 계속 제공) |

### 7.3 설계 포인트
- **LLM이 실패하거나 한도에 걸려도 서비스는 동작한다** — 근거 목록 · 추이 · 계산 결과는 LLM 없이 제공
- 공유 분석 도입으로 호출량이 **사용자 수가 아닌 종목 수에 비례**하게 된다

> ✅ 원인 분석 공통 결과(`stock_event_analyses`)와 사용자별 이벤트(`user_market_events`)는 ERD에서 분리하여 관리한다.

## 8. 운영 지표 — 관리자 영역 ★ 신규

> 사용자에게는 보이지 않는 **관리자 전용** 영역이다.
> LLM 사용량 · API 한도 같은 운영 정보를 사용자 화면에 노출하면 "내가 많이 썼나?" 하는 압박이 되므로 분리한다.

### 8.1 방침
| 항목 | 결정 |
|---|---|
| 제품 내 관리자 화면 | **만들지 않는다** |
| 운영 지표 수집 | Spring Boot Actuator + Micrometer → Prometheus |
| 확인 방법 | Grafana 대시보드에서 관리자가 직접 확인 |
| 부하 테스트 | **하지 않는다** — 배치 중심 서비스라 TPS · 동시접속이 병목이 아님 |
| 목적 | 기능이 실제로 어떤 값을 내는지 확인하고, 결과 보고서의 정량 근거로 활용 |
| 관리자 운영 알림 | 배치 실패 · 외부 API 장애 · 주요 운영 오류, 배포 결과(성공 · 실패)를 **Discord**로 개발자에게 알림 (웹훅 구성 `[구현 시 확정]`) |

### 8.2 수집 지표
| 영역 | 지표 | 확인하려는 것 |
|---|---|---|
| 배치 | 장 마감 → 알림 도달 소요 시간 | 감지 후 5분 이내 발송 기준 충족 여부 |
| 배치 | 단계별 소요 시간 (수집 · 감지 · 분석 · 발송) | 어디서 시간이 걸리는지 |
| 외부 API | 기관별 호출 수 · 성공률 · 평균 응답시간 | CODEF · 한투 · DART · 뉴스 · ECOS 안정성, 일일 한도 대비 사용량 |
| LLM | 일일 호출 수 · 토큰 사용량 · 추정 비용 | 상한 정책이 실제로 지켜지는지, 전역 예산 설정 근거 |
| LLM | **공유 분석 재사용률** | 종목 단위 공유로 호출이 얼마나 줄었는지 |
| 자산 기록 | PARTIAL · FAILED 스냅샷 비율 | 자산 수집이 안정적인지 |
| 원인 분석 | 근거 발견률 · 근거 상태 분포 · NO_EVIDENCE 비율 | 원인 분석이 실제로 쓸 만한 결과를 내는지 |
| 알림 | 채널별 발송 성공률 · 재시도 · DEAD_LETTER 건수 | 알림 파이프라인 신뢰성 |
| 알림 | 발송 억제(SUPPRESSED) 건수 | 발송 상한이 적정한지 |

> 위 목록은 **후보**다. 최종 지표는 기능이 완성된 뒤 정리한다 `[구현 시 확정]`

### 8.3 결과 보고서 활용 예시
- "공유 분석 적용으로 LLM 호출 N% 절감"
- "급등락 이벤트 중 N%에서 근거 1건 이상 발견"
- "감지 후 알림 도달 평균 N분"

> 새 기능을 만드는 것이 아니라 **이미 만든 기능의 결과를 측정하는 장치**다.
> 교수님 목적(아이디어 구현)과 부딪히지 않으면서 구현 결과를 숫자로 보여줄 수 있다.

## 9. 원인 분석 — 표현 제약

| 원칙 | 적용 |
|---|---|
| 단정 금지 | "때문에 올랐습니다" ❌ → **"같은 시점에 이런 일이 있었습니다"** ⭕ |
| 근거 제시 | 모든 원인 후보에 출처 링크와 시각 표시 |
| 근거 상태 표기 | 신뢰 등급을 매기지 않고 결과 상태만 표시: **관련 근거 확인 / 시장 · 업종 동반 움직임 / 관련 근거 확인 불가**. 동반 판단 기준 · 업종 데이터 확보 여부 `[구현 시 확정]` |
| 시간 관계 | 가격 변동 시점과 근거의 발표 · 게시 시점을 함께 고려한다. **장 마감 이후 공개된 자료는 당일 가격 변동의 원인처럼 표현하지 않는다.** 수집 시작 · 종료 시각, 시각 정보가 없는 공시, 장 시작 전 · 장 마감 후 뉴스 처리 `[확인 필요]` |
| 공시 필터 | 가격 변동과 관련성이 낮은 행정성 · 정기성 공시는 원인 후보에서 제외. 포함 · 제외 유형 목록은 DART 실데이터 테스트 후 결정 `[구현 시 확정]` |
| 투자 권유 금지 | 매수 · 매도 의견 없음, 사실 정보 전달과 요약까지만 |
| 원인 불명 허용 | 근거를 못 찾으면 "특별한 뉴스가 없습니다. 시장 전체가 N% 움직였습니다" |

> **억지로 이유를 만들지 않는 것이 신뢰를 만든다.**

## 13. 발표 강조 포인트

1. **"자산 가계부"** — 가계부의 익숙한 경험을 그대로, 기록 대상만 지출에서 자산으로
2. **"왜 움직였는지 설명하는 자산 앱"** — 숫자 나열과의 차별점
3. **알림(재방문) → 원인 분석 · 결산 페이지(체류)** — 사용과 유지를 나눠서 설계
4. **목표 → 예적금의 논리적 연결** — 애매한 자산군 비교 대신 목표 시점 기반 매칭
5. **원인 불명을 인정하는 설계** — 억지 인과관계를 만들지 않는다
6. **LLM 호출이 사용자 수가 아닌 종목 수에 비례** — 공유 분석과 상한 정책

## 14. 확정 / 미결

- 서비스 정의: **자산 가계부** — 자산 변화를 기록하고 분석 · 비교해 자산을 늘리도록 돕는다

- 한국투자증권 API 개인 사용 가능, 나머지 API 한도 수용 범위 내 (뉴스 소스는 후보 단계)

- 월간 자산 결산 **매월 1일** 발송 (웹 푸시 요약 + 텔레그램 전문)
- 운영 지표는 **관리자 전용 Grafana**로 확인, 제품 내 관리자 화면 · 부하 테스트 없음
- 주식 평가금액 최종 기준은 **한투 종가 × 같은 기준 시점의 보유수량** — 일별 기록 기준에 맞춤. 시세 수집 전 연동 초기에는 CODEF 평가액(`resValuationAmt`)을 임시 사용 (미결 #4에서 이동)
- CODEF는 국내 주식과 ETF를 구분해 주지 않는다 → STOCK / ETF는 다른 소스로 판별 — 한투 종목정보 증권그룹으로 확정(2026-10-14, 아래 항목)
- `assets`에는 DB 유니크 제약을 두지 않는다 — 같은 유형 자산 여러 개 허용
- 연동 상태 전이: 검증된 오류 코드에 한해 인증 정보 오류 → AUTH_FAILED, 인증 · 연동 만료 → EXPIRED. 그 외 오류는 상태 유지 + 제한된 재시도. 정기 배치는 ACTIVE 연동만 수집, 재인증 안내는 상태 전환 시에만 생성, 재인증 성공 시 ACTIVE 복구, 수집 제외로 생긴 누락은 PARTIAL / FAILED 정책을 따름
- 예적금 · 입출금 계좌는 이번 범위에서 수기 입력 — 기존 모듈에 수집 기능이 없음, CODEF 은행 수집은 이후 개발 (미결 #22 결과)
- 휴면(DORMANT) 회원 처리는 범위 제외
- 은행 입출금 계좌는 수기 자산의 현금(CASH) 유형으로 등록한다. 수기 자산 등록 기능은 필수(사용자가 등록할지는 선택)이고, 삭제는 과거 기록 보존을 위해 비활성 처리한다
- 증권 수동 새로고침은 **편의 기능**이다 — 현재 자산만 갱신하고 공식 일별 기록 · 결산 · 감지 · 알림은 만들거나 바꾸지 않는다. 사용자 단위 쿨다운을 둔다
- 공식 일별 기록은 그 배치 실행의 수집 결과로만 판정한다. 동기화가 겹치면 배치는 짧게 대기 후 1회 재시도하고, 그래도 실패한 계좌는 누락(PARTIAL / FAILED)으로 처리한다 — 정기 배치를 조용히 건너뛰거나 이전 값으로 COMPLETE를 만들지 않는다
- 수집 값이 없거나 해석할 수 없으면 0으로 채우지 않는다(정상 숫자 0은 유효). 계좌 하나의 동기화 실패는 그 계좌의 실패이고, 다른 유효 자산이 있으면 그날 기록은 PARTIAL이다. 기록할 자산이 하나도 없으면 COMPLETE를 만들지 않는다
- 기관 · 로그인 방식 미지원은 검증되지 않은 사전 차단 목록 없이 CODEF 오류 코드로만 안내한다
- 한투 변동률 (2026-10-14, 미결 #5에서 이동): 전일 대비 변동률은 한투 `prdy_ctrt`를 **그대로** 쓴다 — 기준가(액면분할 · 권리락 반영) 대비라 자체 기업행사 조정 로직을 두지 않는다. 실호출 검증: 2018-05-04 액면분할일 −2.08% (`docs/ops/kis-verification.md` V1)
- STOCK / ETF 판별 (2026-10-14, 미결 #24에서 이동): 한투 종목정보의 증권그룹 `EF` = ETF, `ST` = 주식. 그 외(ETN 등)는 비워 둔다(임의로 주식 처리하지 않음). 시세 수집 때 판별되지 않은 종목만 1회 조회하고, CODEF 재동기화가 이 값을 지우지 않는다
- 일별 기록 판정 (2026-10-14): 거래정지 종목은 직전 거래일 종가로 평가해 **수집 성공**으로 본다 · 수기 자산만 있는 사용자도 기록한다 · CODEF "조회 결과 없음"은 그 계좌 누락으로 본다(임시 — CODEF 실제 응답 확인 후 재검토) · 같은 날 다시 실행해도 이미 COMPLETE인 기록은 더 나쁜 결과로 덮어쓰지 않는다 · 자산군의 대상이 전부 실패하면 그 자산군 금액은 비워 둔다(0이 아님)
- 첫 기록 시점 (2026-10-14): 공식 일별 기록은 **정기 배치에서만** 만든다 — 연동 직후에는 만들지 않고, 연동 뒤 첫 영업일 16:00 배치가 첫 기록이다
- 시장가격 영향 (2026-10-28, 미결 #1 · #2에서 이동): 직전 COMPLETE 기록 대비 (계좌, 종목)별로 **계속 보유한 수량 × 가격 변화**를 종목별 반올림 후 합산한다. 가격은 그날 평가에 쓴 단가(거래정지는 직전 종가). 매수로 늘어난 수량 · 매도로 줄어든 수량은 체결 단가 · 시각을 수집하지 않아 가격 효과를 계산하지 않는다(기타 자산 변화에 포함). 예수금 · 예적금 · 현금은 0. 필요한 수량 · 단가가 없으면 0으로 채우지 않고 비워 둔다. 기간 값은 일별 값의 합. 액면분할일은 합계만 맞고 자체 보정하지 않는다(#5와 같은 방침). 상세는 05 §4.7 · §4.11
- 예금 이자 (2026-10-29, 미결 #3에서 이동): 예금 이자는 별도 식별하지 않고 기타 자산 변화에 포함한다(입출금 · 이자 데이터 미수집)
- PARTIAL · FAILED 화면 표시 (2026-10-29, 미결 #19에서 이동): 그날에는 금액 · 비교 모두 최근 COMPLETE 기록 값을 쓰고, 화면에 기준 날짜와 상태(예: '10/27 기준 · 오늘 일부 자산 조회 실패')를 표시한다. PARTIAL의 부분 금액은 노출하지 않는다
- 알림 채널 (2026-10-11): 사용자는 **웹 푸시(기본, 요약 + 딥링크)** + **텔레그램(선택 — 연결한 사용자에게 같은 알림을 전문으로)**. 이메일은 가입 인증 · 비밀번호 재설정 전용이고 알림 채널은 향후 확장. 디스코드는 사용자 채널이 아니라 개발자용 운영 오류 · 배포 결과 알림

### ✅ v6 확정 (기획 피드백 반영)
1. 총자산 증가와 시장가격에 의한 변화는 구분한다
2. 월급 · 저축 등도 총자산 증가에는 정상적으로 포함한다
3. 확인할 수 없는 기타 자산 증가 원인은 추측하지 않는다
4. 목표 계산에서 최근 3개월 평균 증가액 방식은 제거한다
5. 목표 기본 계산은 현재 자산 + 월 납입액, 수익률 0% 시뮬레이션으로 한다
6. PARTIAL / FAILED 스냅샷은 비교 · 감지 · 결산 계산에서 제외한다
7. 실패 데이터를 직전 값으로 강제 이월하지 않는다
8. 국내 주식 · ETF · 예금 · 적금은 자산 기록 범위에 포함하고 해외 주식은 제외한다
9. ETF 원인 분석은 개별 기업과 동일하게 처리하지 않는다
10. 기존 원인 확신도 4단계는 제거한다
11. 목표 LLM 일 1회 호출은 제거한다
12. 예적금 핵심 기능은 유지하되 우선 정기예금 중심으로 간소화한다
13. ~~사용자 알림은 Web Push + Email 중심으로 한다~~ → **변경(2026-10-11)**: 사용자 알림은 Web Push(기본) + Telegram(선택 · 전문). Email 알림은 향후 확장, Discord는 개발자 운영 · 배포 알림
14. 과거 30일 사용자 총자산 소급 생성은 하지 않는다
15. 실제 사용자 자산 기록은 계좌 연동일부터 시작한다 → **보완(2026-10-14)**: 첫 기록은 연동 뒤 첫 정기 배치(영업일 16:00)가 만든다. 수기 자산만 있는 사용자도 기록한다. 과거 소급은 여전히 하지 않는다
16. 사용자당 일 10건은 **신규 분석 생성 요청** 한도다. 이미 생성된 공유 분석의 재사용은 한도에 포함하지 않는다
